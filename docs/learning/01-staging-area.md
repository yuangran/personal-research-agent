# 第二次动手任务：工作区与暂存区

目标：理解 `git add` 并不是“提交”，而是在选择下一次提交应该包含哪些内容。

## 三个位置

```text
工作区                  暂存区                   本地仓库
你正在编辑的文件  --git add-->  下次提交的快照  --git commit-->  永久提交历史
```

- **工作区**：磁盘上当前看到和编辑的文件。
- **暂存区**：已经选入下一次提交、但尚未提交的快照。
- **本地仓库**：`.git` 中已经创建的提交历史。

同一个文件可以同时拥有工作区版本和暂存区版本。例如先执行 `git add README.md`，然后再次编辑 README；此时新编辑的内容还在工作区，暂存区保留的是执行 `git add` 时的版本。

```bash

```

回答：

完整 diff 较长是正常的。阅读时重点看有没有密钥、私人数据、无关文件，以及改动是否符合本次提交的目的。

## 导师反馈

检查日期：2026-07-27

1. 文件确实从 `Untracked files` 进入了暂存区；`git status` 中显示为 `Changes to be committed`。
2. `git status` 可以说明当前有待提交内容，但要验证提交历史是否真的存在，`git log` 更直接。当前运行它会提示分支还没有提交。
3. 你正确发现了普通 `git diff` 有输出的原因：文件被暂存后又经过编辑。此时 `git diff` 展示工作区相对暂存区的新修改。
4. `git diff --cached` 更准确的含义是：比较暂存快照与当前 `HEAD` 提交。因为本仓库还没有首个提交，它会把暂存内容全部显示为新增。
5. `--stat` 展示文件及增删行数量的摘要；文件处于 `untracked`、`staged` 还是 `modified` 应使用 `git status` 查看。
6. “一个提交只做一件事”不等于“一个提交只能放一种文件”。这批文件虽然用途不同，但共同完成“建立项目与学习骨架”这一个目的，因此适合成为同一个初始化提交。
7. `docs` 是可以解释得通的类型；考虑到此次还包含 `.gitignore` 和仓库初始化，推荐使用 `chore: initialize project learning structure`，它比“只是文档修改”更完整地描述了提交目的。
